EmbedGemma2 per-stage GPU time (G5) and device-memory accounting (G6)
======================================================================
Machine: Apple M5 Pro, 64 GB, macOS 27 (Darwin 27.0.0), 2026-10-15. Library at 60a6240 (branch
worktree-agent-aa4d6ba1364869275, which adds only src/bin/profile_embedgemma2.rs, this file and
its data, and a paragraph in docs/embedgemma2.md; no library code changed). Checkpoint:
google/embeddinggemma-2 snapshot 914f7f89142e33e77833254d9c9b90c3cef7303b. Tool:
target/release/profile_embedgemma2 (src/bin/profile_embedgemma2.rs), analysis by
bench/results/embedgemma2_stage_profile_report.py and ..._plot.py. Data (every raw sample of every
pass and every mode): embedgemma2_stage_profile_m5pro.json. Plot: embedgemma2_stage_profile_m5pro.png.
The stage tables at the end of this file are the report script's output (it also writes them to
embedgemma2_stage_profile_tables.txt, not committed).

Verified = measured here and the output is in the JSON. Inferred = follows from measured numbers by
an argument stated next to it. Unverified = not measured.

SUMMARY
  * G5. In every workload, exact-f32 GEMMs are 52-88 % of a forward. The largest single stages are the
    gate|up GEMM (14-32 %), then, depending on length, the sliding-window attention (up to 16 %) or
    the global attention (27 % at 2x4096), then the qkv and down GEMMs. The elementwise stages
    (norms, residual adds, gelus, rope, scale, gather) together are 10-18 %, and at >= 2048 rows
    each runs at 190-285 GB/s of counted traffic, about the 218-246 GB/s a blit reaches: a faster
    kernel gains little there, only fusion removes the traffic. The GEMMs are compute-bound on the
    f32 TensorOps rate (75-98 % of the 7.4 TFLOP/s a 4096^3 f32 GEMM reaches) at >= 2048 rows.
    With bf16 operands the same shapes run 3.8-4.6x faster (24-29 TFLOP/s) at >= 2048 rows and
    1.9-2.2x at 16 rows (weight-bandwidth side). Attention, 3.5-43 % of a forward, also runs at the
    f32 matrix rate (5.0-6.0 TFLOP/s at >= 256 tokens per sequence). Verified.
  * G6. The cause is isolated and it is three things, not the two guessed. (1) One activation set
    grew from 576 to 736 MiB at 8192 rows (+160 MiB, +27.8 %): the per-layer-input run buffer is
    +240 MiB, the packed gate|up and the dropped normed-V buffer save 80 MiB (the audit's "packed
    gate|up" is a saving, not a cause). (2) Two sets are live
    at once whenever encode is called again without a wait in between: encode's last act is to drop
    its activations, the pool recycles them only at the next commit, and the next encode allocates
    first. So a loop of encodes peaks at 2 x 736 = 1472 MiB, not 736. (3) bench_embedgemma2's
    "device_peak_mib" starts each workload from what the earlier workloads left cached, so the
    three rows 32x256 / 8x1024 / 2x4096 of the committed table are one number (1652), not three
    measurements: 1652.4 = 436.3 (cached by 1x16, 64x32) + 2 x 608.1 (two sets, 128.3 reused from
    the cache). Reproduced to 0.01 MiB below. Verified.

MACHINE STATE AND NOISE
  Other sessions share this GPU and CPU (three other tessl worktrees were running GPU tests, and
  builds and tests of two other repositories were running, during this work), and the GPU is not
  idle in the display sense: ioreg's "Device Utilization %" read 17-75 % with no job of mine
  running, and 0 % in quiet windows.
  The harness therefore waited for any other tessl test or bench binary to exit before each sample
  (libproc scan of the process table), retook samples during which one appeared, flagged what it
  could not make clean, and records the ioreg reading at the start and end of each workload.
  Four passes of the whole stage run were taken (pass 1 12:27-12:45 CDT, passes 2-4 12:49-13:12 CDT
  after the load had gone). Pass 1 is kept in the JSON but excluded from every figure below: the
  GPU was visibly slow in it (64x32 full forward 188.8 ms against 102.9-109.3 ms in the others,
  gate|up GEMM 3.9 against 6.3 TFLOP/s), not through a tessl process the harness could see (the
  slowdown source is unknown). Passes 2, 3, 4 ran at ioreg utilization 0-4 % at start; they
  disagree by up to 9 % (8x1024: 621.5, 567.0, 582.6 ms) and 22 % (2x4096: 832.6, 708.6, 680.5 ms)
  on the whole forward. A stage's figure below is the minimum over every kept sample of the three
  passes (the house method: min-of-N), and the per-class tables show the range of the per-pass
  minima. Treat any figure as good to about +-10 %, and any difference under 10 % between two
  workloads' ranks as noise. The existing bench numbers (embedgemma2_before_after_m5pro.txt, async
  lane: 7.4 / 102.7 / 466.1 / 528.7 / 689.1 ms for 1x16 / 64x32 / 32x256 / 8x1024 / 2x4096) agree
  with the replica's 7.3 / 102.9 / 466.0 / 567.0 / 680.5 ms to about 7 % at every workload.

METHOD (what was timed)
  Stages. The runtime stamps GPU timestamps only at the start and the end of a command buffer
  (take_metal4_stamps; mid-commits and constant-arena reclaims leave no end stamp), and
  new_inference() has none, so a per-dispatch GPU time is not available. Instead the harness holds
  a replica of EmbedGemma2Model::forward built from the library's public kernels (gemm,
  gemm_nt_f32, encoder_attn, segment_mean_rows, l2_normalize_rows, qwen35::{embed_rows_scaled,
  gated_act, attn_qk_norm_rope_columns}, nn::{rms_norm_f32, rms_norm_residual_add_f32,
  scale_f32_inplace}), loaded from the real checkpoint (all 24 layers' weights packed as
  Loader::linear packs them, so the weights cycle through the caches as in an encode). The replica
  runs in async mode (set_async_encode(true)); 1-10 forwards are queued per host wait so the wait is
  a small part of each sample (10 at 1x16, 1 elsewhere); the host's encode time per forward is
  0.13-0.35 ms in every workload, so no workload is host-bound and the GPU time is what is
  measured. It is switched stage by stage with a bit mask over 21 classes:
     full         every class on;
     only:<c>     only class c, every other dispatch skipped: that stage's cost across all its
                  layers with its real shapes, real weights, real dispatch barriers;
     skip:<c>     everything but c (pass 3 only);
     none         no dispatch: the harness floor (0.001-0.012 ms);
     encode       EmbedGemma2Model::encode itself.
  The 5 workloads are timed interleaved (forward order on even rounds, reversed on odd), 9 rounds
  per pass. A skipped stage leaves stale data in its output; the activations are host-zeroed so
  nothing downstream can see a NaN, and GPU time does not depend on values (inferred; the sums
  below are consistent with it).
  Checks. (1) The replica reproduces encode: its embeddings are bit-identical to
  EmbedGemma2Model::encode's on the same tokens at all five workloads (768, 49152, 24576, 6144 and
  1536 values, max abs diff 0; verified, in the JSON as replica_vs_encode). (2) The sum of the 21
  stages' "only" times against the full forward: 106.4 % (1x16), 109.9 % (64x32), 98.8 % (32x256),
  99.7 % (8x1024), 105.9 % (2x4096). The gap on the two small workloads is the per-wait and
  per-class ramp each "only" run pays and the full forward does not (inferred); at the large ones
  the stages add up to the whole within noise. (3) encode() against the replica, by workload
  (1x16 / 64x32 / 32x256 / 8x1024 / 2x4096): 7.82 / 102.28 / 451.84 / 552.27 / 692.55 ms against
  7.30 / 102.92 / 466.05 / 566.97 / 680.48: -3 % to +7 %, inside noise, so the library's per-call
  extras (activation allocation, id upload, readback) cost nothing measurable. The allocation
  churn alone, measured with no forward (mode alloc), is 0.4-0.8 ms per call at every size. A
  forward on freshly allocated, unzeroed activations per call (as encode makes them) against the
  replica's one host-zeroed set, 10 comparisons (5 workloads x passes 2 and 3): -10 % to +10 %,
  no systematic sign. The replica's stage times are therefore the library's within noise.
  The ablation (full - skip) is too noisy to use. Its sum over all 21 stages is 117 / 21 / -13 /
  122 / 78 % of the full forward at 1x16 / 64x32 / 32x256 / 8x1024 / 2x4096 in pass 3, because a
  stage's marginal time (a few ms to 100 ms) sits under the drift between two full-forward
  minima. It agrees with the stage alone for the largest stage (gate|up GEMM: 132 vs 137 ms at
  8x1024, 136 vs 135 at 2x4096) and is not trustworthy below about 10 % of the forward. All
  statements below use the "only" times.
  Dispatches and fixed costs. 369 dispatches per forward at 1x16 and 64x32, 372 at 8192 rows (the
  per-layer-input projection runs in 1 GEMM, or 2 when its 256 MiB run buffer holds 15 layers).
  A 64-element in-place scale (mode gemm): 1.64 us per queued dispatch (min of 9 x 2000 per wait),
  169 us per dispatch when each commits and waits (min of 5 x 100): 369 x 169 us = 62 ms, most of
  the 77 ms between the committed synchronous and queued 1x16 encodes (85 vs 7.4 ms, G1).
  Queued dispatch cost is 369 x 1.64 us = 0.6 ms, 8 % of the 7.3 ms forward.
  Ceilings. The M5 Pro's peak bandwidth and FLOP/s are not stated in anything this repository
  holds and are not used. "Ceiling" below is only what this harness measured on this machine in
  the same session: gpu_copy 256 MiB -> 256 MiB: 218 GB/s (an earlier run 246; the in-place scale
  kernel 228); exact-f32 TensorOps GEMM 4096^3: 7.36 TFLOP/s; bf16-operand GEMM (gemm_bf16, f32
  accumulate) 4096^3: 30.13 TFLOP/s. They are what the library's kernels reach, not hardware
  limits; elementwise kernels below read above the copy ceiling because 16 MiB tensors partly stay
  in the system cache. Machine balance (flop per byte) is 33.7 for exact f32 and 137.9 for bf16.

    1x16 (16 rows)    down GEMM 28.3; per-layer-input GEMMs 18.5; o GEMMs 17.3; gate|up GEMM 13.6; qkv GEMMs 10.9
    64x32 (2048)      gate|up GEMM 31.9; qkv GEMMs 17.9; down GEMM 14.7; per-layer-input GEMMs 13.9; o GEMMs 9.6
    32x256 (8192)     gate|up GEMM 27.6; qkv GEMMs 15.6; down GEMM 12.3; per-layer-input GEMMs 11.0; o GEMMs 8.0

    2x4096 (8192)     attention global 27.3; gate|up GEMM 19.6; attention sliding 15.8; qkv GEMMs 10.9; down GEMM 8.9

    the f32 matrix rate.
    A bf16 weight copy halves the bytes and does not move this: what changes the time is the bf16
    matrix rate (next table). At 2048 rows (64x32) the same: 5.4-6.8 TFLOP/s, AI 114-186.

    gate|up (185 GB/s, 84 % of the copy ceiling) and qkv (122-158 GB/s) come near it. down, o and the

    the time is latency, not bytes. These four are 62 % of the 1x16 forward.

RESULTS: G6, DEVICE MEMORY
  Reconciled to the byte. Device allocated bytes above the loaded model, per fresh process, from
  GpuRuntime::current_allocated_bytes and peak_allocated_bytes (the bench's own meter):
  ledger (mode ledger, one forward, sync after every stage, peak reset around it): no stage allocates
    anything but 0.25 MiB once (the first qkv GEMM, a pipeline); the 372 dispatches use no scratch.
    So the activations are the whole device footprint of a forward. Verified.
  Not an artifact of the allocation meter: the itemized set computed from acts() allocates 736.02 MiB
    in a bare process (mode memory step A), and encode allocates 736.33 MiB the first time: the 0.31
    MiB difference is ForwardIo and rounding.

  Why 1283 -> 1652 MiB:
    a. The activation set grew 576.08 -> 736.08 MiB at 8192 rows (x1.278; 216.4 vs 144.4 at 2048 rows,
       x1.499): HEAD's PLE run buffer 256 MiB against 16 (+240); gate|up packed 128 against gate +
       up + mid 192 (mid now aliases attn) (-64); normed-V buffer gone (-16) = +160. Verified
       (itemized, below; allocation measured).
    b. Two sets are live at once when encode is called again without a wait between. Mechanism
       (verified by the E,E,E,E and E,S,E,S,E rows): encode ends with rt.synchronize() and only then
       drops its activations; Cold buffers return to the pool freelist in drain_cold_recycles, which
       runs inside the next waiting commit; the next encode calls acts() before its first commit, so
       it misses the freelist and allocates a second set (+736.08 MiB in step 1, 0.00 in steps 2-3,
       which reuse the first set's). With rt.synchronize() between the calls the peak is 736 MiB.
       Every caller that loops encode pays this, not only the bench.
    c. The bench starts each workload's peak from the pool's current allocation, which includes the
       freelist cache of the earlier workloads, and keeps the lifetime maximum: 1652.38 = 436.25
       (cached after 1x16 and 64x32) + 2 x 608.06 (the two sets, 128.27 of each reused from the
       cache). Reproduced with PROFILE_PRELUDE=1x16,64x32 (1652.38) and with bench_embedgemma2
       itself rebuilt here (1652.4 at 32x256, 8x1024 and 2x4096; 1472.4 for 8x1024 alone; 64x32:
       433.0 alone, 436.2 after 1x16). So the committed rows "32x256 / 8x1024 / 2x4096" are one
       number measured once, not three. The 2a7cb8b figure fits the same decomposition (2 x 576.08 =
       1152.2, plus about 131 MiB of cache residue = 1283; at 64x32 2 x 144.4 = 288.8 against 291
       recorded). That is inferred: 2a7cb8b itself was not rerun, only its allocation list (git show
       2a7cb8b:src/embedgemma2.rs, acts()) was allocated.
    Of the 369 MiB rise, 2 x 160 = 320 is (a) counted twice through (b); the other 49 is the cache residue
    differing (c).

  Smaller footprint without extra passes (mode memory, mode ple):
    - Wait before returning (or reuse the activations across calls): 8x1024 peak 1472 -> 736 MiB (-50 %),
      bench order 1652 -> 1044 (-37 %). Measured by the S steps; the library change itself is not
      written (not in this lane's scope).
    - set_ple_run_bytes: at 8192 rows 256 MiB -> 64 MiB -> 16 MiB gives a set of 736 -> 544 -> 496 MiB
      (peak with two live sets 1472 -> 1088 -> 992). Time cost, encode() interleaved min of 9:
      32x256 442.8 / 443.8 / 466.5 / 466.9 ms for 256 MiB / 64 MiB / 16 MiB / one layer per run
      (+0.2 %, +5.4 %, +5.4 %; medians 492 / 480 / 481 / 482 ms); 8x1024 568.0 / 556.2 / 556.0 / 562.1
      ms (-2.1 %, -2.1 %, -1.0 %; medians 587 / 584 / 578 / 579). So a 16-64 MiB bound costs between
      -2 % and +5 %, inside the run-to-run noise here: it buys 192-240 MiB per set for nothing
      measurable. (ple 16 MiB and one layer coincide at 8192 rows: one layer is 16 MiB.)
    - Aliasing, inferred from forward() and not built or measured: qkv (96 MiB) is dead once
      attn_qk_norm_rope_columns has run, and gate_up (128 MiB) is written only later, so one
      128 MiB buffer serves both (-96 MiB); mid already aliases attn. With the PLE bound at 16 MiB
      the set would be about 400 MiB (-46 %).

RECOMMENDATIONS (each: expected gain, evidence)
  Gains are upper bounds from the measured shares and rates above, not predictions of a built kernel.
  1. bf16-operand GEMMs (G2). The GEMMs are 52-88 % of a forward and run at the f32 matrix rate
     (6-7 TFLOP/s) against 22-29 measured with bf16 operands. If every GEMM took the measured
     bf16 rate and nothing else changed, the forward would take 0.54 / 0.33 / 0.43 / 0.52 / 0.60 of
     today's at 1x16 / 64x32 / 32x256 / 8x1024 / 2x4096 (1.9x / 3.0x / 2.3x / 1.9x / 1.7x faster), before the
     cost of writing bf16 activations (fuse it into the producing elementwise stage) and before any
     numerics check; the 16-row case gains through bytes (1.9-2.2x per GEMM), the rest through
     the matrix rate. Largest single win available. Needs the precision decision of G2.
  2. bf16 attention matmuls, only together with 1 (same precision decision): attention is 24 % at
     8x1024 and 43 % at 2x4096 at the f32 matrix rate (5.0-6.0 TFLOP/s). With bf16 QK and PV at a
     third of the time (assumed from the GEMM ratio, not measured for attention), 8x1024 would go
     from 0.52 (GEMMs only) to 0.35 of today's, 2x4096 from 0.60 to 0.35. Under exact f32 there is
     little left: attention is already at 67-82 % of the f32 ceiling (<= 1.3x on its share, <= 5-9 %
     of the forward at 8x1024, 2x4096).
  3. Small-M GEMM for the latency workload (new; not on the board). At 16 rows down, o and the
     per-layer-input GEMMs run at 17-22 % of the copy bandwidth (37-48 GB/s) where gate|up reaches 84 %
     with the same code. A kernel for K = 2048 / N = 512 and N = 512 shapes (split-K, or more tiles)
     that reached 70 % of the copy ceiling would take down 2.07 -> 0.66 ms, o 1.26 -> 0.39 ms and
     ple_gate + ple_out 1.22 -> 0.33 ms: 7.3 -> 4.1 ms (1.8x) at 1x16. Applies below about 64 rows
     (AI under 33.7 flop/B); at 64x32 these GEMMs are already compute-bound. Evidence: gemm table at 16
     rows, stage table at 1x16. Helps the bf16 path equally.
  4. Fusion, G7 (value now ranked). Elementwise stages are 10-18 % of the forward and sit at the
     bandwidth roofline, so only removing a pass helps. The candidates and their measured cost at
     8x1024 / 32x256 / 64x32: gelu*up into the gate|up GEMM's epilogue (20.0 / 19.1 / 5.1 ms, and the GEMM
     writes 2048 instead of 4096 columns); the three norm+residual into the o / down / ple_out
     epilogues, whose N = 512 is one full row (14.5 / 14.1 / 3.6 ms); rms_norm into the next GEMM's
     A read (6.8 / 6.7 / 1.8 ms); per-layer-input gelu and scale+norm (12.2 / 11.6 / 3.4 ms). If every
     one became free: 9.4 % / 11.1 % / 13.5 % of the forward at those workloads (7.8 % at 2x4096). The
     GEMM-fused ones cost registers and occupancy, so plan on half: 4-7 %. gemm_epilogue exists
     (src/gemm.rs:858); that it can carry gelu*up over the packed gate|up output is unverified. The
     fusion also removes up to about 170 of 369 dispatches (not counted; 1.6 us each queued is up to
     4 % at 1x16).
  5. Memory (G6): (a) wait before encode returns, or keep the activations across calls: -50 % peak
     in a loop of encodes (measured); (b) PLE_RUN_BYTES 256 MiB -> 16-64 MiB: -192 to -240 MiB per
     set at no measurable time (measured); (c) alias qkv with gate_up: -96 MiB (inferred). Together
     1472 -> about 400 MiB at 8x1024 (-73 %; (c) is inferred, so the end figure is too).
  Not worth doing, measured: a faster elementwise kernel (at the roofline); host-side allocation
  (0.4-0.8 ms per call); the host encode (0.13-0.35 ms per forward, never the limit).

VERIFIED / INFERRED / UNVERIFIED
  Verified (measured here, in the JSON): the replica reproduces encode bit for bit at 5 workloads; stage
  times; sum of stages vs whole; GEMM and attention rates; ceilings; bf16 GEMM rates at the forward's shapes;
  per-dispatch queued (1.64 us) and synchronous (169 us) cost; the activation sets by buffer; the
  memory reconciliation (736.33, 1472.41, 1652.38 MiB reproduced; ledger no scratch); PLE bound cost.
  Inferred: that GPU time is independent of the values (zeroed inputs in the "only" runs); that a bf16
  forward would approach the isolated-GEMM bound; 2a7cb8b's measured peak decomposition; that the
  per-wait/ramp cost explains the 6-10 % excess of the stage sum at the two small workloads; the
  aliasing saving; the bf16-attention estimate; the fusion estimates.
  Unverified: the M5 Pro's hardware peaks (not used); a bf16 forward's accuracy and speed; any
  fusion or small-M kernel; whether skip-ablation could be made to work with more rounds; the cause of
  pass 1's slow GPU; behaviour under other loads (the machine was shared; see MACHINE STATE).
  Not done: GPU timestamp per dispatch (the runtime does not expose it); the ragged workloads of
  bench_embedgemma2 (uniform BxT only here); a run of 2a7cb8b's binary.
