EmbeddingGemma 2 vision tower: per-stage GPU time of encode_images on the real checkpoint
=========================================================================================
Machine: Apple M5 Pro, 2026-10-15, a GPU other sessions share (see the sample counts below).
Data: embedgemma2_vision_profile_m5pro.json (every pass's raw document under its label: every
sample of every variant). Table builder: embedgemma2_vision_profile_report.py.
Tool: src/bin/profile_embedgemma2_vision.rs, one pass per label, 5 rounds, default workloads
"1,8" (BENCH_WORKLOADS): the two goldens' real processor outputs, image 0 (2304 real patches,
2520 padded) alone, and 8 images (cycling the goldens: 2 forwards, 18864 padded rows).
  EMBEDGEMMA2_SNAPSHOT=.../914f7f89142e33e77833254d9c9b90c3cef7303b
  EMBEDGEMMA2_MM_REF_DIR=.../tessl-eg2/target/embedgemma2_mm_ref
  PROFILE_WAIT_S=600 PROFILE_OPERANDS=f32|bf16 PROFILE_JSON=...  profile_embedgemma2_vision
Labels
  before-f32   the library at 433e659 (this lane's merge base), exact f32, built in its own
               worktree with its own target dir; the profile source is this branch's, with the
               stage list that existed there (no bf16 mode, no attention-output cast class)
  after-f32    this branch, GemmOperands::ExactF32 (bit for bit the same output as before-f32)
  after-bf16   this branch, GemmOperands::Bf16
Method: the harness replicates the forward (checked bit-equal to encode_images on every run:
the "soft values bit-equal" lines in the run logs), then times (a) the whole replica ("full"),
(b) each stage class alone on the real shapes and weights of all 16 layers ("only"), min over
samples of ms per call. A sample taken while another tessl GPU process ran is flagged; the
statistics use the unflagged samples when there are any. Shares divide a stage's "only" time by
the sum of all stages' "only" times. Every stage runs alone, so "sum(only)" is 94% to 107% of
the full replica: a stage alone is not exactly its cost inside the forward (cache state,
overlap), which is why the full-minus-skip column of the JSON is kept but not printed.
What this does not show: one pass per label means the "pass range" column is degenerate (min =
max); the spread of a repeated measurement is in embedgemma2_vision_speed_m5pro.txt, whose
paired interleaved rounds are the speed evidence. The before-f32 and after-f32 passes ran at
different moments on a shared GPU: the stage deltas below that are not the rope are inside
that noise (the f32 GEMMs read 5.8 to 6.8 TFLOP/s in every pass).

  down GEMM 15%, qkv GEMM 12%, then qk-norm + axial rope + kv store 4.4% -> 1.8% (8.38 -> 3.10
  ms, the one stage this lane changed for both modes; 5.8% -> 1.8% at 8 images, 85.9 -> 24.8 ms).
  Bf16 (1 image): attention 30%, gate|up GEMM 23%, down GEMM 12%, qkv GEMM 9%, gelu*up 8%, rope
  4.4%, the norm and residual passes 3.3 + 3.8%, o GEMM 3.4%. The bf16 GEMMs run at 24.5 to 26
  TFLOP/s against 5.7 to 6.4 for exact f32; the bf16 attention (encoder_attn_bf16, shared with
  the text encoder) at 13.5 to 14.9 TFLOP/s is now the largest stage.
