# Exact-f32 NN at the 2B MLP up/gate shape: the 4.1 vs 5.7 TFLOP/s gap, reproduced and diagnosed
#
# Machine: Apple M5 Pro, macOS 27.0.1, 2026-10-11 06:49-06:52 UTC. GPU
# otherwise idle; host load average 10-16 (recorded per run below).
# Tree: 120f675 plus the bench lanes and tune variants of b61a765.
# Commands (three runs, separate processes, interleaved within each):
#   TESSL_GEMM_TUNE=1 cargo build --release --bins
#   BENCH_ONLY=f32walk BENCH_ROUNDS=8 BENCH_ITERS=5 BENCH_WARMUP=4 \
#     target/release/bench_gemm_tnnt_tune           # runs A and B below
#   (a third copy of the lane ran inside the walk run of
#   bench/results/gemm_panel_walk_m5pro.txt, same numbers to within 6%)
#   BENCH_LANES=f32 BENCH_ONLY=q35_mlp_up,square_2048,q35_mlp_down \
#     BENCH_ROUNDS=8 BENCH_ITERS=5 target/release/bench_gemm_tile_tune  # run C
#
# The claim (bench/results/f32_exact_coop_m5pro.txt, 2026-09-30, one run on
# the then-blocked tile-tune rig): production's exact-f32 NN ran
# 2048x6144x2048 at 4.1 TFLOP/s against 5.7 at 2048^3, and a 128x64 sg8
# register-accumulator tile ran it 1.37-1.45x faster with the same bits.
#
# Method: interleaved A/B (8 rounds, order reversed every other round, 5
# timed calls per arm per round). Production is `gemm` on f32 operands.
# The other arms run the production 32x32 kernel body (mm_exact_f32) in one
# dispatch under each tile walk: `_linear` (tile_from_linear: Morton on
# square power-of-two grids, row-major otherwise; production's walk on
# 2026-09-30), `_rowmajor`, and `_ph8/_ph16/_ph32` (column panels of 8, 16
# and 32 tile rows; ph16 is tile_walk's 512-row band at 32-row tiles), plus
# `matmul2d_tensorops_f32` itself (production's kernel in one dispatch, on
# tile_walk) and the coop exact tiles. err is against production's output.
#
# Reproduced: under the 2026-09-30 walk the up/gate shape is slow. A:
# 5.06 TFLOP/s (`_linear`) against 5.67 at 2048^3; B: 4.97 against 6.09.
# The GDN in-projection (2048x8224x2048) shows it more: 4.1-4.4 TFLOP/s
# against 6.6-7.0 on panels.
#
# Diagnosis: B is the cause, through the tile walk. At 2048x6144x2048 B is
# K x N f32 = 50 MB (67 MB at N = 8224), past what the GPU keeps cached;
# the grid (192 x 64 tiles of 32x32) is not square, so tile_from_linear
# walks it row-major, and each of the 64 tile rows re-reads all of B from
# DRAM. Evidence, same runs:
# - every column-panel walk restores the square shape's speed: ph8/16/32
#   ran 5.85-6.75 TFLOP/s at the up/gate shape (1.05-1.12x production,
#   1.16-1.24x row-major) and 6.6-7.0 at the GDN in-projection (1.58-1.60x
#   row-major);
# - 2048^3 (B = 16 MB, a square power-of-two grid in Morton order) is
#   insensitive to the walk: every arm within 0.99-1.03x;
# - at MLP down (2048x2048x6144, B = 50 MB but a square grid) Morton keeps
#   it fast and only plain row-major loses (0.87-0.91x).
# The coop 128x64 tiles' 1.37-1.45x on 2026-09-30 is the same effect: a
# 128-row tile re-reads B a quarter as often. Under panels they gain
# 1.04-1.16x over production at up/gate, as at every other shape there
# (bench_gemm_tile_tune run C: 1.07-1.15x up/gate, 0.96-1.02x elsewhere).
#
# Fixed already: tile_walk's column panels (07f6990, 2026-10-03, after the
# claim) are what production's exact-f32 kernels walk by. A walk only orders
# the tiles, so output is bit-identical across every walk arm (same err to
# the last digit), and src/gemm.rs's panel_walk_matches_row_major_chunks_bit_for_bit
# tests that. Production now runs up/gate at 5.6-6.1 TFLOP/s, at 0.92-1.01x
# of 2048^3 in the same run: the gap is closed.
#
# Left, not fixed: production now routes up/gate (and MLP down) through the
# exact-f32 NN split-K (nn_splitk_k_tile: 8 partitions of 256 rows at
# up/gate), which runs at 0.90-0.95x of one panel-walked dispatch of the
# same kernel (production / matmul2d_tensorops_f32: 1.05-1.11x favouring the
# single dispatch). Taking one dispatch there would change exact-f32 output
# bits (err 2.19e-6 between the two routes: K is summed in a different
# order), which this card's exact-f32 bit-identity rule does not allow, so
# it is a follow-up: narrow nn_splitk_k_tile (made for the LM head's dX at
# K = 50304) to shapes it measured faster on.
#
