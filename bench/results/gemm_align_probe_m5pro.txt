# GEMM operand-view alignment probe
#
# Machine: Apple M5 Pro, macOS 27.0.1. Base commit 4e5faac plus the probe.
# Command:
#   MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1 \
#     cargo test --release --lib alignment_probe_report -- --ignored --nocapture
# The run printed "Metal API Validation Enabled" and "Metal GPU Validation
# Enabled", and reported no validation errors.
#
# Method (src/gemm.rs, mod alignment_probe): each kernel family is encoded
# through its raw dispatch helper, below the host's alignment gate. A, B, C
# (and the epilogue bias) are views starting `offset_bytes` into their own
# buffers. For batched runs the base is 0 and every stride is a whole matrix
# rounded to 64 bytes plus `offset_bytes`, so batch i starts i*offset bytes
# off a 64-byte boundary. Non-accumulating outputs start as NaN. Accumulating
# outputs start from one fixed finite C. Each run is compared bit for bit
# with the same kernel at offset 0, which is first checked against an f64
# CPU reference. Shapes: (144, 96, 80) has 64-byte row strides;
# (130, 97, 70) has odd row strides. Both are ragged against every tile.
#
# Result: all 264 runs are bit-identical to their aligned run, including the
# 4- and 8-byte offsets. On this machine, 64 bytes is not a requirement of
# any family: cooperative, accumulate, epilogue or batched. The rule in
# src/gemm.rs (GEMM_VIEW_ALIGN) is 16 bytes for every family. Offsets below
# 16 are recorded here but not relied on.
#
