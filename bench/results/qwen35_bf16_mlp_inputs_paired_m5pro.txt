# (Qwen35Model::random_tower at the 2B's config, bf16, no LM head; begin +

# 2 + 11 rounds of one forward.
#
# Conditions: shared machine. Other agent sessions were running GPU work
# (an ojas decode benchmark, a torch job) and Go benchmarks; ioreg read the
# GPU 95% busy before this run and the 1-minute load average was ~15-27.
# Pairing puts the same load on both lanes within each round, and the
# per-round ratio is the headline; absolute times are inflated against an
# idle GPU (the 1024 forward measured 149 ms in a quieter run at 30% GPU).
#
# Finding: no win. SwiGLU on bf16 inputs is 0.65x (34% faster: 0.27 -> 0.18
# ms at T = 1024, 0.54 -> 0.35 ms at 2048, per layer), but the gate and up
# GEMMs with a bf16 C are 1.06x (+0.13 / +0.24 ms per layer), so the MLP block
# is 1.01-1.02x and the whole 24-layer forward 1.006-1.009x, slower in every
# statistic (median of round ratios, of medians, of mins). The GEMMs are
# compute-bound at these shapes and their f32 cooperative store is nearly
# free; rounding on the store costs more than the halved write saves.
#
# The store was tried two ways, each a frozen binary, interleaved coop,
# scatter, coop, scatter at T = 1024 (GPU 91-99% busy from other sessions):
# through a bfloat destination cooperative tensor (attn_tiled.h's way, kept)
# and by each lane writing its elements at get_multidimensional_index
# (no second cooperative tensor). gate_up_gemms ratios: coop 1.071, 1.077;
# scatter 1.079, 1.068. Forward: coop 1.013, 1.008; scatter 1.006, 1.007.
# Neither is better, so the simpler, precedent form stayed.
#
