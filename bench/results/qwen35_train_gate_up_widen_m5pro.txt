# Training on bf16 storage: packed gate/up and the widened layer input — M5 Pro, 2026-10-10
#
#   target/release/bench_qwen35_layers --paired-gate-up 512 2048
#   target/release/bench_qwen35_train --bf16 512 2048            (op table)
#   QWEN35_2B_SAFETENSORS=... target/release/bench_qwen35_train --bf16-storage --step-only --step=T [--async]
#
# Built at eb24de1 plus the --bf16-storage flag. Conditions: shared machine,
# other agent sessions' GPU work (ioreg 69-100% busy before each run) and a
# 1-minute load average of ~21-27. The paired runs put the same load on both
# lanes; the op table and step times are single-lane and inflated against an
# idle GPU. Checkpoint: Qwen/Qwen3.5-2B (snapshot 15852e8c), bf16 tower.
#
# Since 8ce9ab2 the training forward rounds x2 to bf16 once for both GEMMs,
# so a packed gate|up GEMM now saves one dispatch per call, not a cast.
#
# Finding, packed gate/up (one [T,2048] x [2048,12288] against two
# [T,2048] x [2048,6144], bf16 operands into f32, outputs identical bit for
# bit): 0.91x async and 0.90x sync at T = 2048 (0.37 / 0.51 ms per pair);
# at T = 512, 0.90x sync but 1.07x async (slower). The training step runs
# the pair twice per layer (forward, and the backward's rebuild), 48 per
# step: at T = 2048 that is 18 ms async / 25 ms sync of a 2.65 / 2.88 s
# bf16-storage step (0.7% / 0.9%); at T = 512, +4 ms async, -6 ms sync of
# 0.71 / 1.16 s. The backward's two weight-gradient GEMMs and two dx GEMMs
# would pack the same way (one TN into a [2048, 12288] gradient, one NT);
# not measured. Adopting it changes the weight layout (`gate`, `up` ->
# `gate_up` [hidden, 2 * intermediate]) everywhere the model's parameters
# live: qwen35_params.rs's table and its torch names, the gradient bank,
# AdamW's parts, the loaders. Not started: the step-level gain is under 1%,
# below what the paired step harness resolves on this machine (its rounds
# span +-8% under load, bench/results/qwen35_train_step_after_m5pro.txt).
#
# Finding, the widened layer input: a bf16 model's backward widens each
# layer's saved bf16 input to f32 (one dispatch), the input norm and the
# residual copy read the f32, and rms_norm_bwd reads it again. Removing the
# widen needs all three to read bf16: a bf16-input qwen35_rms_norm and
# rms_norm_bwd (neither exists; rms_norm_bwd's x is f32 only), and the copy
# replaced by a widening copy. The ops it would touch, per layer (ms, median
# of 7, REPS per command buffer):
#
#   T     widen  rms_norm(f32 in)  copy(f32)  rms_norm_bwd  sum
#   512   0.169  0.182             0.163      0.348         0.862
#   2048  0.204  0.237             0.260      0.524         1.225
#
# Their whole time is a hard ceiling on the saving: x 24 layers, 20.7 ms at
# T = 512 (1.8% of the sync step, 2.9% of the async) and 29.4 ms at T = 2048
# (1.0-1.1%). What would really go is the widen dispatch (4.1 / 4.9 ms per
# step) and half the input bytes of the other three, roughly 0.2-0.6% of a
# step, plus 24 of the sync step's 1949 waited commits. Not built: under the
# step harness's resolution, so no committed win is possible to show.
#
