# (04faf93 the bf16-lane cross-entropy workspace, 337fedd grad_sq_norm in
# one command buffer, 628f113 the bf16 bank's head gradient by chunk,
# d4b73c1 the backward's early release, b8d4010 the pool cache evicts a
# larger buffer for a smaller freed one, c5fd930 a delivery reads the bank
# only to add). Checkpoint: Qwen/Qwen3.5-2B (the instruct release; the -Base
# snapshot here has no weights), Qwen3.5-2B-Base's config. Every
# configuration ran under both binaries back to back inside each round:
#
#   BENCH_BINS="before=... after=..." bench/paired_qwen35_step.sh 3 OUT \
#     256:-:sync 256:-:async 256:-:sync:--storage=bf16 256:-:async:--storage=bf16 \
#     2048:-:sync 2048:-:async 2048:-:sync:--storage=bf16 2048:-:async:--storage=bf16
#
# f32 storage runs train_step (fresh gradients, exact f32 operands); bf16
# storage runs train_step_into a bf16 bank (bf16 operands). Load average
# 2-13 (11:23-11:41, logged per run below). Round 2 ran through a
# machine-wide slowdown (every configuration of both binaries 2x slower:
# the max column), so the min of 3 is the comparison.
#
# Findings (min-of-3 per side):
# - bf16 storage: device peak -1.9 GiB in every configuration (T = 2048
#   10.92 -> 8.99 GiB sync, 13.15 -> 11.23 GiB async; T = 256 9.51 -> 7.61,
#   10.31 -> 8.41 GiB), footprint -2.0 to -4.1 GB: no [vocab, hidden] f32
#   head gradient (1.9 GiB), and the pool no longer pinned by the loader's
#   staging buffer. Time unchanged within noise: T = 256 0.681 -> 0.655 s
#   sync, 0.364 -> 0.344 s async; T = 2048 2.583 -> 2.563 s sync,
#   2.432 -> 2.495 s async.
# - f32 storage, T = 2048: device peak 16.36 -> 15.37 GiB sync, 17.50 ->
#   16.54 GiB async; 5.465 -> 5.351 s sync, 5.572 -> 5.461 s async (-2%).
# - f32 storage, T = 256: time unchanged (1.049 -> 1.050 s sync, 0.812 ->
#   0.809 s async), device peak UP 14.30 -> 15.30 GiB (footprint 18.56 ->
#   19.64 GB): with the loader's 1.9 GB staging buffer evicted, the pool
#   caches the step's own freed buffers up to its 2 GiB cap instead of
#   releasing them (train_step_bytes already counts the cap). The trade of
#   b8d4010; the time it buys shows at T = 2048 and on bf16 storage.
# - Traced step: waits and commits unchanged; a bf16-bank step makes 31
#   dispatches more (2070 -> 2101: one head kernel per vocabulary chunk in
#   place of one delivery of the whole embedding).
# - A first run of this pair, before b8d4010 (load 40-90), showed bf16
#   storage T = 256 async 0.369 -> 0.487 s. Bisected to 628f113 and traced to
#   the pool: the 2B loader leaves its f32 [vocab, hidden] staging tensor in
#   the 2 GiB cache, which never evicted, so every buffer the step freed was
#   released and made again (668 fresh buffers, 6.8 GB, in one backward).
#   The old path's d_embed took that bucket and masked it. b8d4010 fixes the
#   pool; in one binary the by-chunk step is then 0.331 s against the old
#   path's 0.367 s, with no fresh buffer.
#
