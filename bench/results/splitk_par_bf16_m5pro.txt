#   production   gemm_tn_bf16 / GemmOperands::Bf16.tn_acc as main shipped

#                one 64x32 multiply_accumulate dispatch per 256 of K)
#   coop_*       one cooperative dispatch over all of K (128x64 overwrite,
#                64x64 accumulate)
#   par_splitk_W every partition of W rows of K one 64x64 cooperative tile
#                set into its scratch slice, then reduce_partitions_f32
#                (reduce_partitions_add_f32 to accumulate)
# (384, 384, 4096) is not gated: production is the cooperative kernel there.
#

#     64x64 accumulate kernel against the sequential lane's per-partition
#     passes). SPLITK_MIN_K is not ported: (2) supersedes both.
# (2) The parallel split-K beats the sequential lane at every gated shape:
#     2.4-19x at its best width, overwriting and accumulating alike (the
#     reduce reads C once more to add). The best width followed the
#     threadgroup count, which src/gemm.rs's tn_par_bf16_k_tile encodes: the
#     widest of 1024/512/256 that keeps >= 32 threadgroups of 64x64 tiles.
#     At the ungated 384x384x4096 control it was 1.43x over the cooperative
#     kernel overwriting and 1.03x accumulating; extending the gate beyond
#     prefer_tn_splitk's shapes is left as a follow-up, unmeasured.
# Decision: prefer_tn_splitk's shapes take the parallel split-K in
# gemm_tn_bf16 and in the bf16 accumulate; the sequential bf16 kernel
